# API SQL Inventory (PostgreSQL)

> Generated by reading every SQL string in `api/modules/**/*.ts` (service.ts, model.ts, controller.ts).
> Source of truth for this document is the code, not the DDL.
>
> **Scope note — two databases.** `api/utils/sql_query.ts` (pg `Pool`) serves the
> PostgreSQL schema documented below. `api/utils/mysql_query.ts` (mysql2, read-only user
> `fts_web_reader`, database `ftsgroupstore`) serves the `legacy_*` modules only; those are
> listed separately in the last section and are **not** part of the PostgreSQL inventory.
>
> `model.ts` files contain no SQL — they are reply field maps. They are cited only where a
> field name they expose has no matching column in any query (see section 6).

**PostgreSQL relations touched: 20** (18 base tables + 2 views: `orders`, `order_details`).

## 2. SQL functions, expressions and casts that must exist server-side

### Built-in functions / expressions used
| Expression | Where |
|---|---|
| `NOW()` | `purchase_orders/service.ts` (UPDATE, update_status), `orders_out/service.ts` (4 statements), `wastrel_ms_plates/service.ts` (UPDATE) |
| `CURRENT_TIMESTAMP` | `timeline_msps|srbs|wmsps|wsrbs/service.ts` (`COALESCE($n, CURRENT_TIMESTAMP)` for `*_event_at`), `purchase-order-detail/service.ts` (`podetail_updated_at = CURRENT_TIMESTAMP`) |
| `COALESCE(...)` | 24 occurrences — `stock_reservations/service.ts` (stock code/status fan-in), `purchase_orders/service.ts` (price maths), all four timeline INSERTs |
| `COUNT(col)` | `count_duplicate` in `master_data/customer`, `master_data/ms_plates`, `master_data/steel_round_bars`, `projects` |
| `SUM(...)` | `purchase_orders/service.ts` LATERAL subtotal/tax/total |
| `concat_ws(' ', ...)` | `purchase_orders/service.ts` (approver name th/en, detail emp name) |
| `jsonb_agg(... ORDER BY ...)` | `purchase_orders/service.ts` LATERAL `details` |
| `jsonb_build_object(...)` | `purchase_orders/service.ts` (detail object + nested `emp` object) |
| `ANY($1::text[])` | `wastrel_ms_plates/service.ts` and `wastrel_steel_round_bars/service.ts` `update_location` |
| `LEFT JOIN LATERAL (...) ON TRUE` | `purchase_orders/service.ts` |
| `WITH <name>_cte AS (...)` | customer, ms_plates, steel_round_bars, purchase_orders, stock_reservations, all four timelines, both wastrel modules |
| `UPDATE ... FROM (VALUES ...) AS values(...)` | `purchase-order-detail/service.ts` `update` |
| `ORDER BY ... NULLS LAST` | `purchase_orders/service.ts` |
| `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` | `wastrel_ms_plates/service.ts`, `wastrel_steel_round_bars/service.ts` — **DDL executed at request time** |

No custom (project-defined) function is *called* from application SQL. The custom generators
(`generate_unique_id()`, `gen_project_display_id()`, `gen_purchase_order_number()`,
`gen_customer_display_id()`, `gen_employee_display_id()`, `gen_wmsp_display_id()`,
`gen_wsrb_display_id()`) are relied on **implicitly** as column DEFAULTs: every INSERT in the
code omits the primary key and omits `po_number`, `project_display_id`, `customer_display_id`,
`wmsp_display_id`, `wsrb_display_id`. If those functions (and their sequences) are absent the
INSERTs fail with a not-null violation.

## 5. Things that would fail on a fresh database

1. **`public.orders` and `public.order_details` are views**, and `orders_out/service.ts`
   **writes** to them: `INSERT INTO public.order_details (...)`, three `UPDATE`s on
   `order_details`, and one `UPDATE` on `orders`. A plain (non-updatable) view or a view over a
   join takes no INSERT/UPDATE without an `INSTEAD OF` trigger or a rule. `order_details` as
   defined in `db/local/schema.sql` is a join over `purchase_orders_details` + `material_masters`,
   so it is definitively **not** auto-updatable.
2. **Columns the code selects from `orders` that the local view does not expose**: the view is
   `SELECT po_id, po_number AS ord_no, po_cus_id, po_status, po_created_at`, but the code reads
   `ord_date`, `ord_due_date`, `ord_status`, `ord_total_items`, `ord_remark`, `ord_cus_id`
   and writes `ord_status`, `ord_updated_at`. Every `orders_out` read would raise
   `column o.ord_date does not exist`.
3. **Columns the code uses on `order_details` that the local view does not expose**:
   `odd_mm_id`, `odd_remaining_quantity`, `odd_created_at`, `odd_updated_at`, `odd_po_id`
   (the view exposes `podetail_po_id`, not `odd_po_id`).
4. **Enum types that exist nowhere**: `public."order_status_enum"` and
   `public."order_detail_status_enum"` are cast to in `orders_out/service.ts` but are not
   created by `db/local/schema.sql` and are not in the documented schema. All four
   `orders_out` write paths fail with `type "public.order_status_enum" does not exist`.
5. **Runtime DDL**: `wastrel_ms_plates/service.ts` and `wastrel_steel_round_bars/service.ts`
   run `ALTER TABLE ... ADD COLUMN IF NOT EXISTS <t>_location text` on the first `get` of the
   process. This requires table-owner privileges for the application role, takes an
   `ACCESS EXCLUSIVE` lock, and silently swallows failures — after which the following SELECT
   of `wmsp_location` / `wsrb_location` errors out.
6. **Implicit dependency on DEFAULT-generating functions and sequences** (see section 2):
   `generate_unique_id()`, `gen_*_display_id()`, `gen_purchase_order_number()` and the
   sequences `project_display_seq`, `purchase_order_seq`, `customer_display_seq`,
   `employee_display_seq`, `wmsp_display_seq`, `wsrb_display_seq`.
7. **Broken SQL — `stock_reservations/service.ts` `soft_delete`** has a stray comma:
   `SET sr_status = 'Deleted',` immediately followed by `WHERE`. This is a syntax error on
   every database; the statement can never have run.
8. **`customers` / `employees` are outside the documented module** but every read path joins
   them, so the schema is unusable without them (the doc lists only `customers.customer_id`
   as an external dependency, and never mentions `employees`, `provinces`, `districts`,
   `subdistricts`).
9. **`purchase-order-detail/service.ts` `create` passes `condition.sql` straight into
   `VALUES ${condition.sql}`.** If the request body is not a non-empty array the fragment is
   empty and the statement becomes `INSERT ... VALUES RETURNING *` — a syntax error rather
   than a validation failure.
10. **Extensions**: none required. No `uuid_generate_v4()`, `gen_random_uuid()`, `pg_trgm`,
    unaccent, or similar appears in application SQL.
11. **Triggers**: none created or called by the API, but the code never sets `*_created_at`
    (except via DEFAULT) and mostly never sets `*_updated_at` — only `purchase_orders`,
    `wastrel_ms_plates`, `orders`, `order_details` and `purchase_orders_details` set it
    explicitly. If `updated_at` maintenance is expected to be a trigger, that trigger must exist.
